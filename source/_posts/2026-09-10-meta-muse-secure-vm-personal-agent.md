Meta 的 Muse 发布稿里有一句话让我停下来多看了几遍：每个用户会得到一台专属云电脑，Agent 和数据都住在里面。这比“个人 AI”具体得多。聊天窗口关掉了，浏览器、文件和登录会话还在，Muse 可以接着干活。

麻烦也从这里开始。一段回答写错了，关掉就行；一台拿着登录会话、半夜仍在运行的电脑做错事，后果已经落到外部网站。我想看的不是 Muse 会不会写计划，而是这台电脑如何留住现场、谁准它往外发东西，以及出问题时能不能查清楚。

## 一台云电脑到底多了什么

普通聊天产品的基本单位是一次回答。它可以记住预算和偏好，却很难靠摘要还原一个做到一半的现场：浏览器开在哪一页，文件下载到哪里，表单填到哪一步，登录会话是否还有效。长任务往往死在这些细节上，不是死在模型忘了目标。

Meta 的发布说明把 Muse Secure VM 定义为一台专属虚拟机，里面有浏览器，并保存 Agent 工作需要的数据和连接凭据。Muse 在这台计算机上打开网页、填写表单和继续跨应用任务。用户关闭应用后，云端现场仍然存在，因此任务可以等待外部变化，再从原位置继续。

“记住目标”和“保留现场”是两回事。预算、偏好和未决问题属于语义状态；文件、浏览器会话和工具进程属于执行状态。只有前者，Agent 每次都得重建环境。只有后者，桌面上会留下一堆东西，却没人说得清它们为什么存在。

Muse 可以等外部变化、继续生成文件，再在需要人判断时发消息。这个能力很实在，也有点让人不安：目标没写截止时间，预算和通知条件也含糊，它就会把一句随口交代的话执行得比人预想得更久。

## Secure VM 解决隔离，不能自动解决授权

一台专属 VM 先把不同用户的运行环境隔开。Meta 表示，连接服务的凭据放在安全存储里，Muse 本身看不到密码或支付信息。用户亲自在浏览器输入的密码，同样不直接暴露给 Agent。

这套设计减少了明文凭据进入对话和模型上下文的机会，但不能把“隔离”偷换成“操作安全”。只要一个已登录会话能够发邮件、提交表单或下单，控制浏览器的 Agent 仍然拥有真实影响力。风险从“它是否知道密码”转为“它能用这个会话做什么”。

这里不能只看“邮箱已连接”。至少还要问：它只能读，还是也能写；这次目标有没有覆盖发送动作；临到发送时，用户是否还要确认。Muse 的官方说明允许用户分别控制读取和发送。这个粒度有用，因为“能看邮件”和“能代表我说话”根本不是同一级权限。

还要留意撤销语义。断开连接能阻止后续访问，却不能撤回已经发出的邮件，也不能保证外部网站同步删除已提交的数据。用户界面如果只给出“停止 Agent”，而没有列出已完成动作、活动连接和后台任务，停止按钮很容易制造虚假的安全感。

## Sentinel 不是护身符，它只是多了一道门

Muse 旁边还有一个 Sentinel Agent。它在系统层面与 Muse 隔离，网络动作先过 Sentinel，需要时再问用户。执行者不能自己给自己盖章，这是这套设计里我最认可的一点。

如果生成计划的 Agent 同时决定“这一步很安全”，一次错误判断就可能直接落到外部系统。增加独立检查层后，执行意图至少要经过另一套策略。发送邮件、购买商品等敏感操作还会显式停住，等待用户批准。图中的审批门就是这个位置。

可它仍然不是护身符。Sentinel 得先理解网页动作的实际含义：一个写着“继续”的按钮可能已经包含订阅，一次看似只读的访问也可能把私人信息带给第三方。页面改版、提示注入、连续几步操作，都可能让单步判断失真。

因此审批界面不能只问“允许 Muse 继续吗”。它至少要展示目标对象、将要提交的数据、金额或收件人、动作发生的网站，以及批准后是否还会连续执行下一步。用户批准的是一项可理解的动作，不是给当前会话发一张空白通行证。

## 审计记录最怕只剩一串绿勾

Meta 说 Muse 会展示完整的计划和动作记录。“完整”这个词很大，我只认能对账的记录。

发送前，要看得到收件人、正文版本和附件；执行时，实际参数得和刚才批准的一样；结束后，记录最好能跳到已发送邮件、订单号或保存文件。三段信息少一段，审计页都可能退化成 Agent 自己写给自己的工作总结。

审计记录还需要区分尝试、成功和未知。网页点击完成不代表服务器接受了请求；浏览器超时也不代表请求没有提交。如果 Muse 在网络中断后简单重试，可能造成两次发送或两笔下单。产品要么能通过外部标识核对结果，要么把状态标成未知并交还用户，不能用一条绿色对勾掩盖不确定性。

长目标还要留下触发原因。它为什么偏偏在此刻继续，是到点了、外部信息变了，还是 Muse 自己觉得该跟进？这几种情况的排查方法完全不同。审计记录不写触发来源，所谓主动性就只剩下一次突然打扰。

## 真要试，我会先给它一个无害任务

我不会一上来就接邮箱、日历和支付。先让 Muse 从三个公开来源做一个对比页面，关掉客户端，过几小时再补一条限制。回来看看它是在原文件上继续，还是又做了一份互不相干的新稿。这个小任务已经能测出云端现场到底有没有延续。

接着可以让它准备一封邮件，但禁止发送；改掉收件人或附件后再看审批卡。变化没有显示，或者上一次“允许”自动覆盖了新动作，权限范围就有问题。

最后故意把事情弄坏：让页面过期，撤销一个连接，任务跑到一半时喊停。此时我想看到明确的失败和剩余活动，而不是“已完成”。Agent 承认自己不知道结果，往往比它顺利跑通一次更能说明产品是否可靠。

## 它省不省事，要看你愿不愿意管它

Muse 适合那些会拖上几天、要在网页里留下东西、中途偶尔需要人拍板的任务。策划旅行、持续整理公开资料、跟进一项个人采购，都比“解释一个概念”更能看出专属计算机有没有价值。

如果任务十分钟内就能完成，输入输出都在一个文档里，普通聊天或一次性 Agent 更省事。若每一步都要确认，用户实际上多了一名需要逐屏监工的操作员。反过来，如果任务牵涉不可逆付款、法律承诺或大量私人数据，也不该因为有 Sentinel 就直接全权托付。

发布资料当然证明不了 Muse 更聪明。它真正拿得出手的是一套运行结构：现场留在云电脑里，敏感动作另过一道门，用户还能回头查。至于这套结构靠不靠谱，顺利演示时看不出来。等登录过期、网页变了、用户反悔了，再看它怎么收场。
